# ADR-002: Route billing by selected xai/ model

## Status

Accepted

## Date

2026-08-20

## Context

Issue #2 says last login `grok_oauth` should call Grok billing and a Vercel last login should keep using Gateway. The user overrode that: any selected `xai/` model uses Grok billing; any other model uses Gateway.

`CreditsLookupInput` currently has only `credential` and `tenant`. `fetchCredits` always calls `fetchGatewayGetResult` against `/coding-agent/v1/credits`.

## Decision

Extend `CreditsLookupInput` with the selected model id. `fetchCredits` calls Grok billing when the model starts with `xai/` and has a non-empty remainder. Otherwise it keeps the existing Gateway credits path. Last-login source does not choose the endpoint.

When the model is `xai/`, refresh the selected credential first, then send `app.auth.apiKey()` / the startup credential as the SuperGrok Bearer with Grok client headers. TUI `preparePromptCredential` must refresh selected `grok_oauth` through `loadGrokLoginCredential` (today `refreshFxLoginIfNeeded` no-ops for any other source). CLI startup already uses `.refresh_if_needed`. Preferred `grok_oauth` refresh failure must not fall through to precedence; `loadGrokLoginCredential` must surface the error instead of returning null. Do not inspect token shape and do not open a dormant Grok session file while another login is selected.

If selected `grok_oauth` refresh fails, `recoverPromptCredentialRefreshFailure` records `grok_oauth`, prints `Run fx login grok.`, and still opens the picker. Do not hardcode `source=fx_login`. If that key is still missing after admission, return `Run fx login grok.` with no HTTP and no invented status. Do not fall back to Gateway on a missing key or a 401/403. When the model is not `xai/`, use the current credential and tenant on the Gateway path.

## Alternatives Considered

### Alternative 1: Last login wins

- **Description**: Branch on `CredentialSource.grok_oauth`.
- **Pros**: Matches the issue text and last-login ownership.
- **Cons**: A Vercel login with an `xai/` model still hits Gateway with the wrong token.
- **Why rejected**: The user chose model-wins.

### Alternative 2: Model plus Grok session

- **Description**: Require both `xai/` and a Grok session file.
- **Pros**: Avoids billing calls with a Gateway token.
- **Cons**: Extra session inspection in the provider.
- **Why rejected**: The user chose model-wins always.

## Consequences

### Positive

- Credits follow the same model prefix already used by `grok_route.forModel`.
- Callers already know the selected model.

### Negative

- A Grok last login plus a non-`xai/` model still sends the active credential to Gateway. If that credential is a Grok token, Gateway 401s with existing Gateway copy.
- A Vercel last login plus `xai/` calls Grok billing with the active Vercel key. Grok 401/403 becomes `Run fx login grok.`
- A selected SuperGrok session past `refresh_after_ms` refreshes before billing. Relogin copy is only for a missing key or a failed refresh.
- Failed `grok_oauth` refresh on the shared admission path records `grok_oauth` and opens the picker. Chat inherits that recovery.

### Risks

- Callers that omit the model default to Gateway and can reintroduce the current 401. Require the model on CLI and TUI fetch sites.

## Implementation Notes

Reuse `std.mem.startsWith(u8, model, "xai/")` plus a non-empty remainder, matching `grok_route.forModel`. The Bearer is `apiKey()` after selected-credential refresh. Do not inspect token shape. Loading `grok_session` is allowed only as that selected `grok_oauth` refresh, never as a side channel while Vercel is selected.
